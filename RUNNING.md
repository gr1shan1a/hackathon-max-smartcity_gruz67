# Запуск и подключение MAX

## Локальная версия

Открыть: http://localhost:5173. API и та же production-сборка: http://localhost:3001.

```bash
python3 scripts/local.py restart
python3 scripts/local.py status
python3 scripts/local.py stop
```

Скрипт пересобирает frontend/backend, управляет только своими процессами и сохраняет базу.
Нужны Node.js 22+, Python 3 и PostgreSQL (`initdb`, `pg_ctl`, `psql`, `createdb` в PATH;
на этом Mac используется Homebrew PostgreSQL 14). Скопируйте `.env.example` в `.env`
при первом запуске; не перезаписывайте существующий токен.
Локальная БД: `127.0.0.1:55432`, база/пользователь `smartcity`, данные `.local/postgres`.
Доступ trust используется только на loopback для локального тестирования.
Логи: `.local/run/`. `stop` останавливает приложение, но оставляет PostgreSQL работающим.
Остановить БД: `pg_ctl -D .local/postgres stop`.

## Docker / сервер

```bash
docker compose up -d --build
# Несколько API-процессов с общей БД:
docker compose up -d --scale backend=3
# Полный перезапуск с новой сборкой:
docker compose up -d --build --force-recreate
```

Frontend: `http://localhost:5173` (переменная `FRONTEND_PORT`). PostgreSQL и API
в Docker доступны только во внутренней сети. `container_name` и фиксированный
внешний порт backend убраны, чтобы разрешить несколько реплик. После изменения
числа реплик перезапустите frontend для обновления DNS nginx:
`docker compose restart frontend`.
Docker daemon на текущем Mac был выключен, поэтому фактический запуск выполнен
локальным скриптом; сборка контейнеров в этой сессии не проверялась.

Том `postgres_data` хранит данные. `docker compose down` его сохраняет;
`docker compose down -v` удалит данные — не используйте для обычного перезапуска.
Для сервера задайте собственный `POSTGRES_PASSWORD` (URL-совместимое значение).

## Тестовые данные и масштабирование

`users` содержит два демонстрационных профиля: житель кв. 47 и председатель кв. 1.
`records` хранит отдельные сущности: заявки, квитанции, показания, встречи, объявления,
пропуска, контакты. Поля владения, ключи и индексы реляционные; содержимое сущностей
хранится в JSONB. `owner_id` с внешним ключом отделяет личные данные пользователей.
`schema_migrations` фиксирует версии структуры и начального наполнения.

```bash
npm --prefix backend run db:migrate
npm --prefix backend run db:seed
npm --prefix backend run build
npm --prefix backend test
```

Seed выполняется один раз, повторный запуск не сбрасывает оплаты, показания,
голоса и не возвращает удалённые записи. Тесты создают отдельную временную схему,
поднимают два API и удаляют схему по окончании, не изменяя рабочие данные.

API не хранит изменяемое состояние в памяти. Пул соединений регулируется
`DB_POOL_MAX`. Транзакции отправляют успешный ответ только после COMMIT.
Блокировки PostgreSQL по коллекции/владельцу защищают от потери параллельных изменений
между репликами. Для большой нагрузки следующий шаг — запросы и блокировки по
отдельным сущностям, пагинация, отдельные таблицы голосов, `building_id` для нескольких
домов, мониторинг и PgBouncer. Сейчас чтение загружает коллекцию целиком, а записи
в общую коллекцию выполняются последовательно. Это основа для развития MVP,
не подтверждение готовности к произвольной нагрузке.

Резервная копия локальной БД:

```bash
pg_dump -h 127.0.0.1 -p 55432 -U smartcity -Fc smartcity > .local/smartcity.dump
```

## Подключение мини-приложения в MAX

Токен из корневого `.env` проверяется без вывода секрета:

```bash
node backend/scripts/check-bot.mjs
```

Проверен бот `se14409794_bot`. Сам токен не публикуется во frontend.
Для поля «Мини-приложение → Введите ссылку» нужен публичный HTTPS-адрес.
После разрешения на публичный доступ к демо можно запустить временный туннель:

```bash
cloudflared tunnel --url http://127.0.0.1:3001 --no-autoupdate
```

Запишите выданный HTTPS-адрес в `MINI_APP_URL` корневого `.env`, перезапустите
приложение и вставьте адрес в поле на скриншоте → выберите кнопку «Открыть» →
«Сохранить». После привязки ссылка входа: https://max.ru/se14409794_bot?startapp.
Туннель работает только пока запущен процесс и доступен компьютер; после
перезапуска адрес может измениться. Для постоянного размещения используйте
сервер с Docker Compose, домен и TLS-прокси перед frontend.

Публичный туннель создан с разрешения владельца:
https://leads-worked-pic-least.trycloudflare.com
Адрес записан в MINI_APP_URL. Webhook зарегистрирован в MAX, меню команд обновлено.
Сохраните этот адрес в поле мини-приложения в кабинете MAX, чтобы работала кнопка
открытия внутри мессенджера. Через Bot API этот параметр не устанавливается.

Официальная инструкция: https://dev.max.ru/help/miniapps.

## Границы демо

`DEMO_MODE=true` разрешает выбирать тестовый профиль. Идентификатор сохраняется
в браузере и передаётся заголовком `X-Demo-User`; это не аутентификация. Выбор
профиля в одном браузере не меняет пользователя в другом. После выбора заново
загружаются все данные и очищаются состояния форм. Ошибки API больше не подменяются
успешными операциями в локальном кэше.

Перед реальными жильцами необходимы проверка MAX initData на сервере, привязка
MAX ID к подтверждённой квартире, роли и отключение демо. При `DEMO_MODE=false`
демонстрационные API закрываются (403), пока реальная авторизация не реализована.
Оплата и сообщения соседям остаются симуляциями. Сам бот работает через настоящий
MAX Bot API: отвечает на входящие команды и нажатия кнопок. Автоматическая доставка
сообщений соседям и персональных счетов требует отдельной привязки MAX ID к квартире.

## Работающий бот

После изменения HTTPS-адреса (не меняйте токен):

```bash
python3 scripts/local.py restart
npm --prefix backend run bot:setup
```

`bot:setup` проверяет публичный healthcheck и защищённый webhook, регистрирует
подписку на `bot_started`, `message_created`, `message_callback` и команды
`/start`, `/app`, `/tickets`, `/bills`, `/sos`, `/help`. Если зарегистрирован чужой/старый
URL, скрипт остановится: проверьте и удалите именно устаревшую подписку через API
перед повторной регистрацией. Обычный рестарт приложения не меняет туннель или подписку.

Webhook проверяет `X-Max-Bot-Api-Secret`, сохраняет событие в `bot_updates` и сразу
отвечает MAX. Работник (`MAX_BOT_ENABLED=true`) отправляет ответы, повторяет временные
ошибки до 10 раз с задержкой и не теряет очередь при перезапуске. Повторная доставка
одного события не создаёт новую запись. Если процесс прервётся между отправкой MAX
и фиксацией результата в БД, возможен повторный ответ (внешний API не даёт транзакции
вместе с нашей БД). Логи — `.local/run/backend.log`, ошибки доставки — `bot_updates.error`.
`/tickets` читает публичные заявки из рабочей БД, `/bills` ведёт к счетам в приложении,
не выдавая чужой лицевой счёт за привязанный к собеседнику.

В этой среде проверен `https://platform-api.max.ru`, он задан в `.env`. Текущая
документация рекомендует `https://platform-api2.max.ru`; местный Node не доверяет
его цепочке сертификатов. Для перехода установите официальный CA в отдельный PEM,
задайте `NODE_EXTRA_CA_CERTS` при запуске Node и смените `MAX_API_BASE`. TLS-проверка
не отключалась; глобальное системное хранилище сертификатов не менялось.

Тесты: `npm --prefix backend run build`, `npm --prefix backend run test:bot`,
`npm --prefix backend test`. Автотесты не отправляют сообщения реальным пользователям.
Документация: https://dev.max.ru/docs-api/methods/POST/subscriptions,
https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard.

## Обновлённая навигация и пропуска

В нижнем меню четыре вкладки: Главная, Сервисы, Заявки, Профиль.
Каталог сервисов разделён на Дом и платежи, Автомобиль, Соседи и Помощь;
поиск находит сервис по названию и типичным словам («барахолка», «счётчик» и т. д.).
Парковка отделена от квитанций: Сервисы → Автомобиль → Моя парковка.

Пропуск создаётся с датой/временем приезда по Москве и сроком 4, 8 или 24 часа.
В API доступны интервалы от 1 до 72 часов и планирование до 180 дней вперёд.
Даты новых пропусков хранятся в ISO 8601 UTC; старые записи читаются без сброса.
Пропуск сохраняется в личном списке, открывается повторно, содержит QR и код,
может быть отправлен через системное меню или скопирован. Запланированные и
действующие пропуска находятся во вкладке «Актуальные», завершённые и отменённые —
в «Архиве». Отмена доступна владельцу, данные не удаляются.
QR содержит идентификатор пропуска; подключение к физическому шлагбауму по-прежнему
не входит в демо.

Регрессионные тесты покрывают даты, длительность, сохранение при перезапуске и
запрет отмены чужого пропуска. UI проверен в отдельном Chrome на 320–430 px:
вкладки, поиск, оформление, QR, повторное открытие и архив без ошибок JavaScript.
